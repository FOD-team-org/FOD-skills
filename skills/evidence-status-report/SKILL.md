# 확인한 것만 보고하기

## 언제
- "어디까지 됐나", "다 됐나", "지금 상황", "왜 이런가" 같은 질문.
- 사람이 의견을 내며 동의를 구할 때.
- 작업을 끝내고 마지막 보고를 쓸 때.

## 순서
1. 답하기 전에 지금 확인한다: 프로세스 생존, 진행 로그 마지막 줄 시각과 현재 시각, 산출물 개수와 수정 시각, 테스트·측정 출력.
2. 시각은 기억이 아니라 `date` 같은 명령 출력으로 쓴다. "멈췄냐"는 질문에는 마지막 출력 시각, 프로세스 생존, 산출물 수 세 가지로 답한다.
3. 항목마다 상태를 하나 단다: 확인됨(근거 붙임), 미확인(무엇을 보면 확인되는지), 실패(증상과 출력).
4. 원인을 말할 때는 가설과 확인을 나눈다. 가설에는 확인 방법을 붙인다.
5. 사람이 원인 가설을 냈으면 그 가설부터 시험하고 결과를 적는다.
6. 근거가 사람 생각과 다르면 결론과 함께 대안을 하나 이상 낸다.
7. 질문의 목적(조사, 결정, 한계 확인)이 불분명하면 먼저 묻는다.

## 형식
| 항목 | 상태 | 근거 |
|---|---|---|
| 렌더 12편 중 9편 | 확인됨 | 출력 폴더 파일 9개, 마지막 수정 HH:mm |
| 남은 3편 | 진행 중 | 프로세스 살아 있음, 로그 마지막 줄 N분 전 |
| 실패 1건 원인 | 가설 | 디스크 부족 추정, 남은 용량 확인 예정 |
- 표 아래에 다음 행동 한 줄, 사람이 정할 것 한 줄(없으면 생략).
- 숫자는 직접 센 값만 쓴다. 손으로 센 값은 스크립트로 다시 센 뒤 쓴다.
- 비교를 말할 때는 비교 대상과 기준값을 같은 표에 둔다.
- 시간 제한으로 끊긴 결과는 통과로 쓰지 않는다. WARN이나 FAIL로 쓰고 끊긴 지점을 적는다.
- 코드 검증 결과는 실행·통과, 정적 확인만, 실행 못 함으로 나눠 쓴다(scoped-change-verification).

## 확인
- "확인됨" 칸마다 명령·파일·수치 근거가 있다.
- 하위 에이전트 보고를 옮긴 칸은 직접 확인했거나 "에이전트 보고, 미확인"으로 표시했다.
- 지난 보고와 달라진 것이 있으면 정정 문장이 맨 위에 있다.

## 하지 않는 것
- "아마 끝났을 것", "정상으로 보임"처럼 확인 없는 완료를 쓰지 않는다.
- 문서 근거 없이 플랫폼 정책이나 동작을 단정하지 않는다. 틀렸으면 정정한다.
- 쓰는 중일 수 있는 파일(JSON·측정 결과)을 수정 시각만 보고 완료로 판단하지 않는다. 파싱되는지, 항목 수가 맞는지 본다.
- 동기화 폴더의 수정 시각은 바뀔 수 있다. 판단은 파일 내용으로 한다.
- 긴 로그를 붙여 넣지 않는다. 핵심 줄만 인용한다.
