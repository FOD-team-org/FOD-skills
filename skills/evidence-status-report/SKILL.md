# 근거 있는 상태 보고

우선순위: 실행 환경의 시스템 프롬프트·설정 > 사람의 지시 > 이 스킬. 부딪혀 결과가 달라졌으면 보고에 적는다.

## 순서
1. 질문이 무엇을 알고 싶은지(진행률·원인·다음 할 일) 한 줄로 다시 적고, 조사 목적이 둘 이상으로 읽히면 먼저 묻는다.
2. 답하기 전에 지금 상태를 직접 잰다.
   - [ ] 현재 시각: `date`
   - [ ] 로그 마지막 줄과 그 시각: `tail -n 3 <로그>`
   - [ ] 산출물 개수·크기·mtime: `ls -la --time-style=full-iso`
   - [ ] 프로세스 생존: PID 조회
   - [ ] 데이터 상태: DB 조회나 `curl` 응답
3. 답은 아래 표 형식으로 쓰고, 칸마다 근거(명령·파일·수치·시각)를 붙인다.
   | 상태 | 근거 | 확인 시각 |
   |---|---|---|
4. 재지 못한 칸은 "미확인"과 이유(권한 없음·API 지연 등)를 쓰고 추정으로 채우지 않는다.
5. 원인 진단은 "가설"과 "확인됨"을 나눈 두 목록으로 쓰고, 가설마다 확인할 명령을 붙인다.
6. 사람이 원인을 짚으면 동의하기 전에 그 가설을 시험하는 명령을 돌리고 결과를 함께 답한다.
7. 결론에는 근거 1개 이상과 대안 1개 이상을 붙인다.
8. 완료 보고 전에 아래 허위 완료 점검을 모두 통과시킨다.
9. 앞선 보고·안내가 틀렸으면 다음 보고 첫 줄에 "정정:"으로 틀린 내용과 맞는 내용을 쓴다.
10. 컨텍스트 압축·모델 교체 뒤에는 기억 대신 상태 파일과 작업 기록을 다시 읽고 재개한다.

## 점검
| 허위 완료 점검 | 기준 |
|---|---|
| 실행 여부 | "실행 중"이라고 쓰기 전에 PID와 로그 증가를 확인한다. |
| 산출물 갱신 | 메타 파일의 생성 시각 필드와 산출물 mtime이 이번 실행 뒤인지 본다. |
| 결과물 직접 보기 | 영상·이미지·화면 결과는 직접 열어 본 뒤에만 "문제 없음"이라고 쓴다(`visual-output-qa`). |
| 해시·크기 | 보고에 쓰는 해시·크기는 `sha256sum`·`stat`으로 직접 잰 값만 쓴다. |
| 비교 수치 | 점수·지표를 비교하면 비교 대상과 기준값을 표로 나란히 두고 한 번 더 대조한다. |
| 계산 | 합계·비율은 손으로 셈하지 않고 `python`으로 다시 계산한 값만 쓴다. |
| 결함 판정 | "버그"라고 쓰기 전에 입력이 제대로 조립돼 들어갔는지 먼저 확인한다. |
| 사람의 제보 | 사람이 본 증상도 로그·DB·`curl`로 재현하거나 재현 실패를 적는다. |
| 첨부와 파일 | 채팅 첨부와 폴더 파일이 같다고 단정하지 않고 해시나 크기로 비교한다. |
| 정책·규정 | 외부 정책을 말할 때는 원문 위치를 붙이고, 없으면 "확인 안 된 정책"으로 쓴다. |
| 지연 데이터 | 집계 API가 0을 주면 지연 가능성을 적고 재조회 시각을 정한다(`performance-insights`). |
| 서브에이전트 보고 | 위임 결과는 `delegation-loop`의 반납 검수를 거친 것만 옮긴다. |

## 하지 않는 것
- 확인하지 않은 상태를 "될 것이다"·"정상일 것이다"로 보고하지 않는다.
- 사람의 의견에 근거 없이 맞장구치지 않는다.
- 틀린 이전 보고를 조용히 덮지 않는다.
- 로그 한 줄의 완료 문구만 보고 끝났다고 하지 않는다.
- 긴 원시 로그를 그대로 붙이지 않고 근거가 되는 줄만 인용한다.
