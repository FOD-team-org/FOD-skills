# 예약 작업 운영

작업을 어떻게 짤지(실행 방식, 시간 예산, 실패 정지, 등록부 일괄 변경)는 scheduled-job-design, macOS 등록은 launchd-ops를 따른다.

## 언제
- 새 루틴·스케줄러 작업을 등록할 때
- 루틴이 안 도는 것 같거나 결과가 안 쌓일 때
- 앱 데이터 초기화 등으로 등록 목록이 사라졌을 때
- 실행 때마다 콘솔 창이 뜬다는 말을 들었을 때
- 루틴의 모델·설정을 바꿔 달라는 요청을 받았을 때

## 등록할 때
1. 작업 본문(프롬프트·스크립트)과 일정(cron·트리거)이 어디에 저장되는지 확인한다. 본문은 파일, 일정은 앱 데이터처럼 따로 있는 경우가 있다.
2. 등록 직후 목록을 조회해 일정·다음 실행 시각을 확인한다.
3. 등록 정보(이름·일정·모델·작업 폴더·본문 경로)를 운영 문서 표에 한 줄로 남긴다.
4. 첫 실행이 도구 권한 프롬프트에서 멈출 수 있다. 사람에게 수동 실행 1회로 미리 승인하게 안내한다.
5. 같은 산출물을 쓰는 다른 루틴이 있는지 본다. 새 규칙이 다른 루틴의 가드와 부딪히는지 확인한다.
6. 게시하는 루틴은 safe-publish 기준을 따른다.

## 백업
- 등록부 파일(일정 저장소)과 본문 폴더를 정기적으로, 그리고 손대기 전에 복사한다.
- 백업은 앱 데이터 밖(홈 폴더 아래 등)에 둔다. 앱 데이터는 앱 오류로 통째로 다시 만들어질 수 있다.

## 멈춤 감지
| 신호 | 확인 방법 |
|---|---|
| 마지막 실행 | 등록 목록의 최근·다음 실행 시각, 루틴 세션 기록의 시각 |
| 산출물 | 루틴이 쓰는 로그·장부의 마지막 기록 시각 |
| 비교 | 일정상 있어야 할 실행 수와 실제 실행 수 |
- 산출물 시각은 파일 안에 기록된 시각으로 판정한다. 동기화 폴더는 파일 수정 시각이 바뀔 수 있다.
- 멈췄으면 원인(권한 프롬프트 대기, 토큰 만료, 경로 변경, 비활성화)을 확인해 보고한다. 꺼진 이유가 기록에 없으면 다시 켜지 말고 묻는다.

## 등록부 복구
1. 남아 있는 본문 폴더부터 백업한다.
2. 과거 세션 기록에서 가장 최근 목록 조회 출력을 찾아 이름·일정·모델·작업 폴더를 복원한다.
3. 반복 작업만 자리표시 본문으로 다시 등록한다.
4. 원본 본문 파일을 바이트 그대로 덮어쓴다.
5. 목록을 조회해 수와 일정이 복원 근거와 같은지 확인한다.
- 이미 실행된 1회성 작업은 다시 등록하지 않는다. 다시 돌면 게시 같은 일이 되풀이된다. 본문 파일만 보존한다.

## 숨김 실행 (Windows)
- 배치 파일을 직접 걸면 실행마다 콘솔 창이 뜨고, 사람이 침입이나 오류로 오인한다.
- 숨김 래퍼(wscript + VBS 등)로 건다. 파이썬에서 자식 프로세스를 띄울 때는 창 없음 플래그(CREATE_NO_WINDOW)를 쓴다.
- 래퍼로 바꾸면 운영 문서에 "창이 안 뜨는 것이 정상"이라고 적는다. 점검 때 래퍼 프로세스를 이상 프로세스로 진단하지 않는다.
- 작업이 가리키는 파일을 옮기면 스케줄러 인자와 시작 폴더도 같이 바꾼다.
- 오래돼 보여도 현역 작업(토큰 갱신·지표 수집 등)은 지우거나 끄지 않는다. 지우기 전에 그 작업의 산출물을 누가 쓰는지 grep한다.

## 설정 변경
- 모델·추론 강도·권한 같은 루틴 설정은 사람이 앱 UI에서 바꾸는 것이 가장 확실하다. 바꾸는 위치를 안내한다.
- 등록부 JSON 직접 수정은 사람이 요청했을 때만 하고, 절차(백업, 대상 칸만 바꾸기, 되돌리기)는 scheduled-job-design의 등록부 일괄 변경을 따른다.
- 거부된 우회(앱 내부 역공학 등)는 다시 시도하지 않고 멈춰 보고한다.
- 루틴이 운영 규칙 문서를 직접 고치게 하지 않는다. 규칙 변경은 제안으로 남기고 채택은 사람이 한다.

## 확인
- [ ] 목록 조회 결과의 수·일정이 운영 문서 표와 같다
- [ ] 활성 작업마다 최근 실행 시각이 일정과 맞다
- [ ] 백업이 앱 데이터 밖에 있다

## 하지 않는 것
- 1회성 작업 재등록
- 요청 없는 모델·설정 변경
