# 프로젝트 문서 체계

## 언제
- 새 프로젝트를 시작할 때. 사람이 문서화부터 하라고 할 때.
- 문서가 여러 곳에 흩어져 다른 실행자가 무엇을 따라야 할지 모를 때.
- 문서와 실제 동작이 다를 때.

## 시작 구조
| 파일 | 담는 것 |
|---|---|
| AGENTS.md / CLAUDE.md | 프로젝트 지침: 실행 규칙(인터프리터 이름, 인코딩, 줄바꿈), 금지, 세션 시작·종료 때 읽을 것과 남길 것 |
| 요구 문서(PRD) | 목적, 사용자, 기능, 수용 기준 |
| 판단대기 | 사람이 정할 항목만. 아래 형식 |
| 작업 정본(runbook) | 실행 순서, 기본값, 검증 수치, 고장 대응, 경로 지도 |
| docs/작업일지 | 날짜별 한 일, 검수 결과, 다음 할 일 |
| docs/결정기록 | 답을 받은 판단 항목의 질문·답 원문과 반영 위치 |
| docs/위임명세 | 위임할 때 쓴 명세 원본 |
| docs/가이드 | 사람이 직접 할 일 안내(user-task-guide) |
- 새 세션은 지침, 작업 정본, 판단대기, 작업일지 순으로 읽고 바로 이어 갈 수 있어야 한다.
- 반복된 실수는 지침에 한 줄로 넣고, 위임 명세에도 복사되게 한다.

## 판단대기 문서
- 올리는 것: 틀리면 서비스에 문제가 되는 보안·결제·법무·외부 계정·운영 항목, 진행 중에 전제가 무너진 것.
- 그 밖의 판단은 에이전트가 정하고 가정 기록에 한 줄 적는다.
- 항목 형식: ID, 배경 한 줄, 선택지, 추천과 이유, 추천대로 두면 생기는 일(코드 용어 없이 한 문장).
- 사람은 번호로 답한다. 답과 이유 칸은 사람이 쓴다. 비어 있으면 채우지 않는다.
- 답이 모호하면 해석을 밝히고 다시 묻는다. 답을 받으면 결정기록으로 옮기고 반영 위치를 적는다.
- 답을 기다리는 동안의 임시안은 보수적인 쪽을 고르고 이유를 적는다.
- 개발 프로젝트는 judgment 스킬의 형식을 쓴다.

## 작업 정본(runbook)
- 한 작업에 정본 문서 하나만 둔다. 같은 내용을 다른 문서에 복사하지 않고 링크한다.
- 다른 실행자(다른 모델, 다른 사람)가 그대로 따라 할 수 있게 쓴다: 명령, 기본값, 기대 출력, 실패하면 할 일.
- 정책(생성·검수 기준, 금지 목록)과 실행법을 같은 문서 체계 안에 둔다.
- 기본 순서(단계마다 볼 것, 넘어가는 기준)와 상황별 할 일 표로 쓴다. 분 단위 시간표는 쓰지 않는다.
- 사람이 볼 설계도에는 흐름, 파일 지도, 증상별 먼저 볼 곳(고장 지도), 검수 지점(단계·볼 파일·넘어가는 기준)을 둔다.
- 도구·모델·설정이 바뀌면 정본도 같은 작업 안에서 고친다.

## 리서치 저장소
- 폴더 구조와 규칙을 README에 쓴다. 기존 파일은 옮기고 지우지 않는다.
- 판단·기록용 저장소와 제작 폴더를 나눈다. 큰 미디어 파일은 넣지 않는다.
- 주제·실험 문서는 템플릿으로 쓰고, 상대 링크가 깨지지 않았는지 검사한다.
- 한 채널·한 제품 전용으로 만들지 않는다.
- 형식을 일괄 변환할 때는 형식을 먼저 정하고, 백업과 시범 범위를 정한 뒤에 한다.

## 사람이 읽는 문서의 형식
- 제목·표·체크 목록·짧은 구만 쓴다. 한 칸에 사실 하나.
- 후보 비교는 후보 목록에 고른 것과 버린 것을 체크하고 이유·근거를 적는다.
- 설명용 줄글은 쓰지 않는다. 서술은 사람이 직접 한다.
- 이름은 사람이 읽을 수 있게 짓는다. 같은 이름을 여러 대상에 쓰지 않는다.

## 문서와 실제가 어긋날 때
1. 실제 동작을 실측한다(명령 출력, 파일).
2. 어느 쪽이 맞는지 정한다. 사람이 정할 일이면 판단대기에 올린다.
3. 틀린 쪽(코드 또는 문서)을 고친다. 문서는 정본 한 곳만 고친다.
4. 작업일지에 무엇이 어긋났고 어디를 고쳤는지 적는다.
5. 지침 문장 때문에 결과가 이상해졌으면 원인 문장을 찾아 적용 범위를 좁힌다.

## 확인
- 새 세션이 문서만 읽고 다음 할 일을 말할 수 있다.
- 판단대기에는 열린 항목만 있고, 답을 받은 항목은 반영 위치와 함께 결정기록에 있다.
- 사람이 읽는 문서에 설명용 줄글 문단이 없다.
