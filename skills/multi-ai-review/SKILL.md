# 여러 AI 토의·검수

## 언제
- 기획·전략·문서 평가처럼 정답이 없는 판단에 두 번째 의견이 필요할 때.
- 사람이나 메인이 쓴 글·대본의 자연스러움을 다른 모델에게 검수받을 때.
- 한 모델만 쓰니 결과가 비슷비슷하게 나올 때.

## 토의 라운드
| 라운드 | 하는 일 |
|---|---|
| R1 독립 제안 | 모델마다 같은 브리프로 따로 답한다. 서로의 답을 보여 주지 않는다 |
| R2 교차 반론 | 답을 바꿔 보여 주고 약점·반례를 찾게 한다 |
| R3 수렴 | 남은 안, 버린 안, 버린 이유를 정리한다 |
| R4 파일럿 설계 | 남은 안마다 작게 시험할 방법과 판정 기준을 정한다 |
- 라운드마다 브리프 파일과 결과 파일을 남긴다. 다음 라운드는 앞 결과 파일을 읽게 한다.
- 근거가 약한 주장은 실행 에이전트가 따로 조사하거나 작은 시험으로 잰다.
- 최종 정리는 사람이 고를 후보 표로 만든다: 후보, 고른 것·버린 것, 이유, 근거.

## 질문 형식
- 브리프에 목적, 대상 독자, 이미 버린 안과 이유, 판단 기준을 넣는다.
- "좋은지"를 묻지 않는다. 약점 3개, 고칠 문장, 고쳤을 때 잃는 것을 묻는다.
- 수치·출처를 내게 할 때는 출처 URL과 원문 문장을 같이 내게 한다.
- 검수 모델은 읽기 전용으로 둔다. 업로드나 외부 호출을 시키지 않는다.
- 호출이 사용 한도 오류로 막히면 사람에게 알리고 다른 모델로 바꾼다.
- 검수는 헤드리스 CLI로 돌린다. 브라우저 붙여넣기 방식은 실패가 잦고 무인 실행에 맞지 않는다.

## 채택 필터
검수 결과는 그대로 쓰지 않는다. 항목마다 아래를 모두 통과해야 채택한다.
- 근거가 있다: 원문·데이터로 확인된다. 모델이 든 수치·URL은 직접 다시 확인한다. 없는 출처를 지어내는 일이 있다.
- 재현된다: 지적한 문제가 실제 결과물에서 보인다.
- 범위 안이다: 요청 범위와 정해 둔 규격을 바꾸지 않는다.
- 사실을 더하지 않는다: 원문에 없던 사실·기관·고유명사를 끼워 넣지 않았다.
- 뜻을 바꾸지 않는다: 단어를 바꾸며 뉘앙스가 달라지지 않았다.
- 톤을 지킨다: 비속어나 과한 유행어로 바꾸지 않았다.

## 안정 편향 대응
- 서로 반박하는 토의는 반박을 버티는 무난한 안으로 모인다. 새로움 기준을 따로 두고 그 기준으로 다시 본다.
- 모델의 기각 판정에 바로 동의하지 않는다. 기각된 안도 후보 표에 남겨 사람이 보게 한다.
- 무난한 여러 개보다 위험해도 센 소수를 남긴다.
- 결과가 획일적이면 모델 계열을 섞는다.

## 코드 교차 검수 라운드
- 라운드마다 새 대화로 시작한다. 앞 라운드의 맥락이 판단을 끌고 가지 않게 한다.
- 결과 첫 줄은 APPROVE 또는 CHANGES REQUIRED. 지적은 `[HIGH|MED|LOW] 파일:줄 내용` 형식이고, 지적마다 ID(예: CX-<작업>-01)를 붙인다.
- 검수자는 고치지 않는다. 고치는 쪽이 ID별로 반영·기각과 이유를 적는다.
- 라운드 상한(3~4회)을 미리 정한다. 넘으면 남은 지적을 사람에게 올린다. 상한 없이 수십 라운드를 돈 적이 있다.
- 한 모델만 본 커밋은 나중에 다른 계열 모델이 한 번 더 본다.
- 구현 에이전트는 커밋하지 않는다. 메인이 APPROVE를 확인하고 커밋한다.

## 확인
- 채택한 항목마다 통과한 필터와 근거가 적혀 있다.
- 기각한 항목과 기각 이유가 남아 있다.
- 모델이 낸 수치·출처를 직접 다시 확인했다.

## 하지 않는 것
- 최종 채택을 모델 다수결로 정하지 않는다. 사람이 고른다.
- 취향 판정(go/no-go)을 모델에 맡기지 않는다.
- "이미 자연스럽게 썼으니 검수 생략"으로 건너뛰지 않는다. 정한 검수는 형식과 상관없이 돌린다.
