# 가설 실험

결과를 본 뒤에 기준을 맞추지 않도록, 판정 방법을 먼저 적고 그대로 판정한다.

## 언제
- 성과가 정체되어 다음 방향을 골라야 할 때
- 두 가지 이상 안을 비교본으로 만들어 고를 때
- 시스템 프롬프트·스킬·플레이북을 고치고 효과를 재야 할 때. 나빠지지 않았는지 정기적으로 지키는 일은 agent-regression-harness
- LLM 기능(분류·추출·요약)을 붙이기 전에 모델과 비용을 정할 때

## 계획서 (실행 전에 파일로 쓴다)
| 칸 | 쓰는 것 |
|---|---|
| 번호·가설 | 무엇을 바꾸면 무엇이 어떻게 달라진다고 보는가 |
| 기준선 | 지금 버전을 같은 조건으로 잰 값 |
| 변수 | 바꾸는 것 하나 |
| 고정 조건 | 입력 세트·시드·브리프·측정 시점·도구 버전 |
| 팔(arm)·표본 수 | 비교안 목록, 안마다 몇 개를 재는가 |
| 판정 규칙 | 채택·기각·보류를 가르는 수치 조건 |
| 중단 조건·비용 상한 | 멈추는 조건, 쓸 수 있는 호출·크레딧 |

## 순서
1. 기준선을 먼저 잰다. 기준선 없이 새 안만 재지 않는다.
2. 계획서를 저장한다. 판정 규칙과 표본 수는 결과를 본 뒤 바꾸지 않는다. 바꿔야 하면 새 번호로 다시 시작한다.
3. 정본은 백업만 하고 새 안은 버전 번호를 붙인 새 파일·폴더로 만든다. 언제든 되돌릴 수 있어야 한다.
4. 대조군과 새 안은 같은 입력·같은 시드·같은 브리프로 돌린다. 한 번에 한 변수만 바꾼다.
5. 자동 감사(정규식·수치)는 참고로만 쓴다. 감사 기준이 낡았으면 감사부터 고친다.
6. 판정 규칙대로 결론을 낸다. 표본이 계획보다 적으면 결정하지 않고 "보류"로 두고 표본을 늘린다.
7. 후보는 나란히 놓아 사람에게 올린다. 탈락 후보도 지우지 않는다. 사람이 고른 안은 고른 그대로(바이트 동일) 반영하고, 반영 전에 "개선"하지 않는다.
8. 새 안 결과가 나쁘면 즉시 이전 버전으로 되돌린 결과를 다시 만들어 비교한다.

## 블라인드 판정 (글·대본·생성물처럼 사람 눈으로 고를 때)
- 새 안과 대조군을 섞고 이름을 가려, 맥락을 모르는 평가자(새 에이전트 또는 다른 사람)에게 평가를 받는다.
- 통과는 "사전 기준 이상"과 "대조군보다 높음"을 둘 다 만족할 때다.
- 실패하면 평가 사유만 고쳐 다시 판정한다. 사유 밖의 것을 함께 바꾸지 않는다.

## 프롬프트·스킬·문서 반복 개선
- 같은 측정 세트로 잰다. 결과 지표, 과정 지표, 토큰 수·단계 수를 함께 기록한다.
- 비교안 사이에 차이가 나면 첫 응답의 해석이 어디서 갈렸는지 찾아 기록한다.
- 실패가 한 번뿐이면 규칙을 늘리지 않는다. 사람 검수 지점으로 돌리고, 같은 실패가 반복될 때 규칙으로 만든다.
- 결과가 이상하면 지침에서 원인 문장을 찾는다. 포괄 문장은 적용 범위를 좁히고 "해당 없을 때 할 일"을 적는다.
- 글자 수 한도는 주지 않는다. 한도를 주면 모델이 한도까지 채운다.
- 반영 전에 과적합을 점검한다: 특정 측정 항목 전용 문장, 정답·전용 코드가 지침에 들어갔는지.

## LLM 기능 스파이크
- 후보 모델 2개 이상을 같은 정답 세트(사람이 확인한 표본)로 비교한다.
- 기본은 드라이런이다. 실제 호출은 명시 플래그가 있을 때만 한다. 키가 있다는 이유로 실호출하지 않는다.
- 실호출이 연속 2회 실패하면 중단하고 보고한다.
- 한 번 호출로 같이 뽑을 수 있는 필드는 합친다.
- 결과는 모델별 정확도·건당 비용 표로 남기고, 채택은 사람이 한다.

|---|---|---|---|---|---|---|---|---|

## 확인
- 계획서 저장 시각이 첫 결과보다 앞선다.
- 판정이 계획서의 규칙과 같은 말로 설명된다.
- 탈락 후보와 이전 버전이 남아 있다.

## 하지 않는 것
- 결과를 본 뒤 판정 기준·표본 수를 바꾸지 않는다.
- 두 변수를 한 번에 바꾸지 않는다.
- 표본이 작은데 "경향이 보인다"로 채택하지 않는다.
