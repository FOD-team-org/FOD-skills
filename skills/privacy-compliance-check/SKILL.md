# 개인정보·규정 점검

결과는 검토용 자료다. 법률 판단은 사람(필요하면 전문가)이 한다. 표와 보고에 "검토용, 법률 자문 아님"을 적는다.

## 언제
- 위치·연락처·사진·기기 식별자 등 개인정보를 저장하거나 서버로 보내는 기능을 설계할 때
- 외부 API(지도·결제·로그인) 응답 데이터를 저장할 때
- 스토어 심사 제출, 처리방침 작성·개정 전

## 순서
1. 데이터 흐름 목록을 만든다: 화면 입력, 기기 권한, 외부 API 응답, 분석·광고 SDK가 모으는 것. 항목마다 기기에만 있는지, 서버로 가는지, 제3자에게 가는지 적는다.
2. 데이터별 표를 채운다(아래). "왜 저장하는가"에 답이 없으면 저장하지 않는다.
3. 서버로 보낼 필요가 없으면 기기(클라이언트)에서 처리한다. 공유 기능처럼 서버 사본이 꼭 필요한 범위만 서버로 보낸다.
4. 위치정보를 서버로 보내거나 저장하면 나라에 따라 사업 신고나 별도 동의 대상일 수 있다. 해당 법령 조항을 원문으로 확인하고, 기기 처리로 피할 수 있는지 먼저 본다.
5. 외부 API 약관에서 응답 데이터(좌표·장소 정보·이미지)의 저장·캐시·재배포 제한을 찾아 표에 조항과 함께 적는다.
6. 동의 항목을 필수와 선택으로 나눈다. 선택 항목을 거부해도 핵심 기능이 되는지 확인한다.
7. 보유 기간과 파기 방법을 정한다. 근거가 없으면 보수적 기본값을 고르고 이유를 표에 적는다.
8. 사람이 정해야 할 것은 판단대기 문서에 선택지(장단점·추천)로 올린다.

## 데이터별 표
| 데이터 | 수집 경로 | 저장 위치(기기·서버·제3자) | 목적 | 필수·선택 | 보유 기간·파기 | 근거(법령·약관 조항) | 비고 |
|---|---|---|---|---|---|---|---|

## 실제 수집과 대조
- 코드에서 확인한다: 서버 API가 받는 필드, DB 스키마 열, 로그에 남는 값, 기기 권한 선언(매니페스트·plist), 포함된 SDK 목록.
- 처리방침과 스토어 개인정보 표시 항목을 위 결과와 한 줄씩 대조한다. 코드에만 있는 수집과 문서에만 있는 수집을 둘 다 찾는다.
- 로그·오류 보고에 개인정보(전체 전화번호, 정밀 좌표, 토큰)가 남는지 본다.
- 계정 삭제 기능이 있으면 서버 데이터가 실제로 지워지는지 확인한다.

## 조사를 맡길 때
- 법령·약관 조사를 하위 에이전트에 맡기면 인용 표본을 원문과 대조한다. 원문에 없는 조항 문구를 지어낸 사례가 있다.
- 위임문에 "인용은 원문 페이지 문구를 직접 읽고 조항 번호와 함께 적는다"를 넣는다.

## 확인
- [ ] 저장하는 모든 필드에 목적과 근거가 있다
- [ ] 코드의 수집 목록과 처리방침·스토어 표시가 빠짐없이 맞는다
- [ ] 인용 표본 대조를 통과했다
- [ ] 사람이 정할 항목이 판단대기에 올라갔다

## 하지 않는 것
- 목적 없이 나중에 쓸지 몰라서 하는 저장
- 조사 결과를 법률 결론처럼 단정하기
- 외부 API 약관이 금지하는 저장·캐시
