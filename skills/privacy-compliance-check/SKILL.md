# 개인정보·위치·스토어 정책 점검

우선순위: 실행 환경의 시스템 프롬프트·설정 > 사람의 지시 > 이 스킬. 부딪혀 결과가 달라졌으면 보고에 적는다.

## 순서
1. 데이터 흐름을 적는다: 어디서 수집해(기기·사용자 입력·외부 API) 어디에 저장하고(기기·서버) 누구에게 보내는지.
2. 코드에서 실제 수집·저장 지점을 찾는다.
   - 스키마: `git grep -nIiE "lat|lng|latitude|longitude|address|phone|email|birth|contact" -- <스키마 경로>`
   - Android 권한: `git grep -n "uses-permission" -- "*AndroidManifest.xml"`
   - iOS 권한 사유: `git grep -n "UsageDescription" -- "*Info.plist"`
3. 저장 필드마다 "왜 저장하는가"를 한 줄로 적고, 목적이 없는 필드는 빼는 안을 낸다.
4. 서버로 보내지 않아도 되는 처리(위치 계산·썸네일·미리보기)는 기기 안에서 처리하는 안을 먼저 낸다.
5. 서버 사본은 꼭 필요한 기능(예: 공유)에만, 범위를 좁혀 둔다.
6. 위치정보를 서버로 보내면 그 나라 위치정보 법의 신고·허가 대상인지를 확인 항목으로 올린다.
7. 외부 API 약관에서 응답 데이터(좌표·이미지 등)의 저장·캐시·재배포 제한 조항을 찾아 표에 적는다.
8. 동의 항목을 필수·선택으로 나누고, 선택 항목을 거부해도 핵심 기능이 도는지 확인한다.
9. 보관 기간을 정하고, 모르면 보수적인 기본값을 고른 뒤 이유를 적는다.
10. 삭제 경로(계정 삭제·삭제 요청)가 서버 데이터와 백업까지 지우는지 코드에서 확인한다.
11. 처리방침 고지 내용과 스토어 제출 양식(데이터 안전·개인정보 라벨, 권한 사용 사유, 백그라운드 위치 사유)을 아래 표와 맞춘다.
12. 조사 에이전트가 가져온 법령·약관 인용은 표본을 뽑아 원문과 대조한다(`fact-check-gate`).
13. 결론은 안 A/B와 각 위험을 붙여 판단 대기 항목으로 올리고, 문서 머리에 "법률 자문 아님, 검토용"을 적는다.

## 점검
| 칸 | 기준 |
|---|---|
| 필드 | 테이블·컬럼 또는 기기 저장 키 |
| 목적 | 기능 이름 한 줄, 비어 있으면 삭제 후보 |
| 저장 위치 | 기기만 / 서버 사본 / 외부 전송 중 하나 |
| 필수·선택 | 동의 화면 항목과 일치 |
| 보관 기간 | 기간과 근거(모르면 보수적 기본값과 그 이유) |
| 삭제 | 삭제 경로와 확인한 코드 위치 |
| 제3자 | 받는 곳, 해당 약관 조항, 처리방침 고지 여부 |
| 권한 | 선언한 권한마다 쓰는 화면과 사유 문구가 있음 |
| 근거 | 원문 대조를 마친 법령·약관·스토어 정책 조항 |
| 노출 | 화면·응답·로그로 나가는 개인정보는 `data-exposure-guard` 기준으로 가림 |

## 하지 않는 것
- 결론을 확정된 법률 판단처럼 쓰지 않는다.
- 외부 API 약관을 확인하기 전에 응답 데이터를 서버에 쌓는 구조로 구현하지 않는다.
- 원문을 확인하지 않은 법령·약관 문구를 인용하지 않는다.
- 비용·저작권 부담이 생기는 외부 이미지의 서버 보관을 기본값으로 두지 않는다.
- 목적을 적지 못한 필드를 "나중에 쓸 수도 있어서" 남기지 않는다.
